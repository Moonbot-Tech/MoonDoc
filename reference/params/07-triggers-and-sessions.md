# Master → Slave Triggers and Session Management (Triggers & Session)

> **Related sections:** [Architecture of triggers and Master → Slave links](../../concepts/04-triggers-and-master-slave.md) · [Examples of scout and ladder links](../../examples/strategies/04-master-slave-scout-and-ladders.md) · [Parameter matrix by trade phase](../parameters-by-lifecycle.md) · [Alphabetical TSV index](index.tsv)

This reference describes 31 parameters for coordinating strategies through signal keys (`Triggers Master / Slave`, numbers `1..202`; `201` and `202` are taken by Moon News) and for managing the order size and pauses by the accumulated financial result of a series of trades (`Session`). Both mechanisms are checked **before** the `IgnoreFilters` switch, so they work even with `IgnoreFilters = YES`.

---

## 1. Generating and clearing keys by the master strategy (Master Triggers)

The master strategy (`Master`) writes the current timestamp into the selected key (`1..202`) on one of four events: a signal detect, an actual buy, a trade closed with a profit or a trade closed with a loss. Triggers require the Autotrading module or the terminal's global Emulation mode enabled (the `EmulatorMode` checkbox of an individual strategy is not enough); without them the conditions are silently skipped. Keys survive a terminal restart if it was down for less than an hour; after a longer pause all keys are reset.

| Parameter | Type · Default | Meaning, formula and key interactions |
| :--- | :--- | :--- |
| **`TriggerKey`** | `int · 0` | Number of the key (`1..202`, `0` — off) activated at the moment the master strategy's **detect fires**; for most detects — also with `AutoBuy = NO`. **Exceptions:** `MoonShot` has no such field at all — it places the order without a detect and passes the key through `TriggerKeyBuy`: on the buy, and with `ActiveTrigger = YES` also while the order waits in the order book; `MoonStrike` gives the detect key only when it is itself ready to enter (`AutoBuy = YES` and `OrderSize > 0`) — emulation mode turns it into a sensor that needs no money; the manual `Manual` strategy activates the key when a buy is placed and only with `ActiveTrigger = YES`. By default the key is active only on the signal coin (or on all markets with `TriggerAllMarkets = YES`). |
| **`TriggerKeyBuy`** | `int · 0` | Number of the key (`1..202`) activated when the **`Buy` order fills**. **Trap in `MoonShot`:** with `ActiveTrigger = YES` enabled, the `MoonShot` strategy keeps `TriggerKeyBuy` active the whole time the limit `Buy` order stands in the order book — that is, **before** the actual buy. |
| **`TriggerKeyProfit`** | `int · 0` | Number of the key (`1..202`) activated after a trade closes with a positive profit (`profit > 0`, including a profitable close by `SellByCustomEMA`). |
| **`TriggerKeyLoss`** | `int · 0` | Number of the key (`1..202`) activated after a trade closes with a loss **or at zero** (`profit <= 0`). The same number in `TriggerKeyProfit` and `TriggerKeyLoss` gives a "trade closed" key regardless of the result. |
| **`ActiveTrigger`** | `bool · NO` | Keeps the key active (`TriggerKeyBuy` for `MoonShot`, `TriggerKey` for the others) the whole time the master strategy is waiting for a buy: both when a real `Buy` order stands in the order book and when the strategy waits for the virtual `BuyStop` / `BuyLimit` level to be crossed — slave strategies are allowed to enter before the exchange order is placed. After the buy fills or is cancelled, the key is not extended; slaves finish their `TriggerSeconds` from the last extension. Combined with `ClearTriggersBelow` / `ClearTriggersAbove`, it clears the neighboring keys on every extension. |
| **`TriggerAllMarkets`** | `bool · NO` | With `YES`, activates the trigger key globally on all trading pairs of the exchange at once; with `NO` — only on the coin where the master strategy fired. |
| **`ClearTriggersBelow`** | `bool · NO` | When key $N$ is activated, clears all keys with strictly smaller numbers ($1 \dots N - 1$). For example, with `TriggerKey = 2` only key `1` is cleared. Used for step-by-step cascades. |
| **`ClearTriggersAbove`** | `bool · NO` | When key $N$ is activated, clears all keys with strictly greater numbers ($N + 1 \dots 202$) — including the news keys `201` and `202`. |
| **`ClearTriggerKeys`** | `string · ''` | Space-separated list of key numbers that are forcibly cleared when this strategy's own non-zero trigger fires (`TriggerKey* > 0`); with a zero event key the clearing is not called, and it acts on all events of the strategy (detect, buy, profit, loss). A non-numeric item in the list is only written to the log and does not block entries. With `TriggerAllMarkets = NO`, listing the strategy's own key in `ClearTriggerKeys` clears it on this coin, but with `TriggerAllMarkets = YES` the global loop over all markets activates key $N$ again. |

## 2. Starting, blocking and emergency exit of the slave strategy (Slave Triggers)

The slave strategy (`Slave`) checks the activity of the allowing (`TriggerByKey`) and blocking (`TriggerKeysBL`) keys on the coin. Key strings support an individual lifetime override in seconds via an equals sign (`1=300 5 7=900`); a non-numeric key number in `TriggerByKey`, `TriggerKeysBL` or `SellByTriggerBL` forbids the slave any new entries (in the log — `Wrong TriggerByKey` / `Wrong TriggerKeysBL` / `Wrong SellByTriggerBL`); an error in the time part (`1=abc`) does not block — the key lives for the common time.

| Parameter | Type · Default | Meaning, formula and key interactions |
| :--- | :--- | :--- |
| **`TriggerByKey`** | `string · ''` | Space-separated list of allowing keys (for example, `1 5 12`, or with an individual lifetime `1=300 5 7=900`). By default works by `OR` logic (one active key is enough). |
| **`TriggerByAllKeys`** | `bool · NO` | Switches the `TriggerByKey` check to logical `AND` mode: the slave strategy starts only when **all** keys listed in `TriggerByKey` are active on the coin at the same time. |
| **`TriggerSeconds`** | `int · 60` | Base lifetime (in seconds, up to `864000` s) for keys from `TriggerByKey` that have no individual timer set via `key=time`. |
| **`TriggerKeysBL`** | `string · ''` | Space-separated list of blocking keys (the trigger blacklist); supports the `key=time` format (`1=300 5`). While at least one of these keys is active on the coin, the strategy opens no new trades. Also serves as the mandatory outer filter for `SellByTriggerBL` and `CancelByTriggerBL` to work. |
| **`TriggerSecondsBL`** | `int · 0` | Lifetime (in seconds) of a blocking key from `TriggerKeysBL` written without its own `=time`. **The default is `0`, and a key with zero time is not in effect for a single second:** it does not block entry, does not cancel buys by `CancelByTriggerBL` and does not sell by `SellByTriggerBL`, even if written in all three fields. In the example `1=300 5`, key `5` does nothing with the defaults. Give every blocking and emergency key a time directly in the list (`102=120`) or a non-zero `TriggerSecondsBL`. |
| **`SellByTriggerBL`** | `string · ''` | Space-separated list of keys whose activation closes the open position. The field accepts **numbers only** — the entry `102=120` here counts as an error and forbids entries. **Two mandatory conditions:** the key must also be listed in `TriggerKeysBL` (the emergency sell is checked only among blocking keys) and have a non-zero lifetime (`102=120` in `TriggerKeysBL` or `TriggerSecondsBL > 0`). The exit follows the same path as the sell on leaving the filters: with `SellByFiltersDelay` set, the take-profit is first moved to the market, then `Panic Sell` turns on by this strategy's stop (`StopLossSpread`, `AllowedDrop`, `UseMarketOrder`). |
| **`CancelByTriggerBL`** | `bool · NO` | Cancels standing `Buy` orders and conditional orders (`BuyStop` / `BuyLimit`) when any key from `TriggerKeysBL` activates. Needed by strategies with `CheckAfterBuy = NO`: `MoonShot` and strategies with `CheckAfterBuy = YES` cancel buys on a blocking key even without this checkbox. A buy already filled by the exchange cannot be cancelled by the key. |

## 3. Profit/loss control and order scaling by session (Session)

The session mechanism keeps a separate cumulative profit-and-loss counter of the strategy for each coin, automatically scaling `OrderSize` on a streak of wins or losses and halting trading for `SessionPenaltyTime` when the drawdown limit is reached. The session check is not disabled by the `IgnoreFilters = YES` flag — it has its own switch, `IgnoreSession = YES`.

**Progression formulas for the thresholds and the order size.** The progression is enabled only by a non-zero counter: with `SessionPlusCount = 0` (default) the growth of the order and of the profit threshold is off, with `SessionMinusCount = 0` (default) — the reduction of the order and the shrinking of the loss threshold. With the default counters, `SessionIncreaseOrder`, `SessionReduceOrder`, `SessionStratIncreaseMax` and `SessionStratReduceMin` have no effect. For the progression to start from the first session, set the counter to `1`.
* **Linear growth of the profitable session threshold** (starting from session `Counter >= SessionPlusCount`):
  $$\text{Max}_{\text{eff}} = \text{SessionStratMax} \cdot \left(1 + (\text{Counter} - \text{SessionPlusCount} + 1) \cdot \frac{\text{SessionStratIncreaseMax}}{100}\right)$$
* **Hyperbolic shrinking of the negative session threshold** (starting from `MinusCounter >= SessionMinusCount`):
  $$\text{Min}_{\text{eff}} = \frac{\text{SessionStratMin}}{1 + (\text{MinusCounter} - \text{SessionMinusCount} + 1) \cdot \dfrac{\text{SessionStratReduceMin}}{100}}$$
* **Exponential scaling of `OrderSize`:** on a streak of profitable sessions the order is multiplied at each step by $(1 + \text{SessionIncreaseOrder}/100)$ (but not above $\text{OrderSize} \cdot (100 + \text{SessionIncreaseOrderMax})/100$), and on a streak of negative sessions it is **divided** by $(1 + \text{SessionReduceOrder}/100)^{n}$, where `SessionReduceOrder` is a positive percentage and $n$ is the number of the negative session counting from the `SessionMinusCount`-th; the divisor is capped from above at $1 + \text{SessionReduceOrderMin}/100$ (default `500` → not less than `1/6` of the base `OrderSize`). Negative values of both parameters are zeroed by the terminal when saved, and the reduction turns off.

| Parameter | Type · Default | Meaning, formula and key interactions |
| :--- | :--- | :--- |
| **`IgnoreSession`** | `bool · YES` | Disables blocking and order scaling by the rules of the `Session` tab (sessions are off by default: `YES`). Does not reset the already accumulated counter, it only ignores the limits based on it; with `YES` the `SessionResetTime` decay does not work either. |
| **`SessionLevelsUSDT`** | `bool · YES` | Units of the `SessionStratMax` and `SessionStratMin` thresholds: with `YES` — a fixed amount in the quote currency (`USDT`), with `NO` — a percentage of the base `OrderSize` (with `OrderSize = 0` the base is `10 $`, so set an explicit `OrderSize` when using percentages). |
| **`SessionStratMax`** | `double · 0` | Profit target threshold of one session (`>= 0`; the comparison is strict, and **zero does not disable the mechanism** — with `0` any profitable trade closes a profitable session). When the threshold is exceeded, the profitable sessions counter is incremented by `+1`, the negative sessions counter is reset to `0`, the current session profit is reset, and the strategy continues working. |
| **`SessionStratIncreaseMax`** | `int · 0` | Percentage of linear increase of the `SessionStratMax` threshold with each next profitable session, starting from `SessionPlusCount` (`0` — the threshold does not change). Has no effect with `SessionPlusCount = 0`. |
| **`SessionStratMin`** | `double · 0` | Loss limit of one session (set as a **negative number**, for example `-100`; the comparison is strict, with `0` any losing trade closes a negative session and starts the pause). When the result goes below the threshold, the negative sessions counter is incremented by `+1`, the profitable one is reset to `0`, the session profit is reset, and the strategy pauses for `SessionPenaltyTime`. If orders opened earlier close at a loss after the reset, the penalty may fire again. |
| **`SessionStratReduceMin`** | `int · 0` | Percentage of shrinking of the allowed loss threshold `SessionStratMin` (a positive number) with each consecutive negative session, starting from `SessionMinusCount`. Has no effect with `SessionMinusCount = 0`. |
| **`SessionResetOnMinus`** | `bool · NO` | Reset the accumulated positive profit of the current session after the very first losing trade, if its loss exceeded `|SessionStratMin| / 10`. |
| **`SessionPenaltyTime`** | `int · 0` | Pause of the strategy on the coin (in seconds) after a negative session is closed by the `SessionStratMin` threshold. |
| **`SessionPlusCount`** | `int · 0` | Number of consecutive profitable sessions starting from which the increase of the order size (`SessionIncreaseOrder`) and of the profit threshold (`SessionStratIncreaseMax`) turns on. **`0` (default) — the progression is off**, not "from the first session"; for the order to grow right after the first profitable session, set `1`. Any negative session resets the profitable sessions counter to `0`. |
| **`SessionMinusCount`** | `int · 0` | Number of consecutive negative sessions starting from which the reduction of the order size (`SessionReduceOrder`) and the shrinking of the loss threshold (`SessionStratReduceMin`) turns on. **`0` (default) — the reduction is off**; for the order to shrink right after the first negative session, set `1`. Any profitable session resets the negative sessions counter to `0`. |
| **`SessionIncreaseOrder`** | `int · 0` | Percentage of exponential increase of `OrderSize` on each profitable session starting from `SessionPlusCount` (`0` — off; with `SessionPlusCount = 0` also has no effect; the actual change is written to the log as `OrderSize increased by ...`). |
| **`SessionIncreaseOrderMax`** | `int · 500` | Maximum addition to the order in `%` of the original `OrderSize` (ceiling `OrderSize * (100 + SessionIncreaseOrderMax) / 100`; the value `500%` means growth of at most 6 times — `+500%` to the base; allowed range `0 .. 5000%`). |
| **`SessionReduceOrder`** | `int · 0` | **Positive** percentage of `OrderSize` reduction for each negative session starting from the `SessionMinusCount`-th: the order is divided by `(1 + SessionReduceOrder / 100)` for each next negative session (`20`: 1000 → 833 → 694; `100`: 1000 → 500 → 250). `0` — off; with `SessionMinusCount = 0` also has no effect. A negative value is zeroed when saved, and there is no reduction. The actual size is visible in the log: `OrderSize reduced by ...`. |
| **`SessionReduceOrderMin`** | `int · 500` | Division limit in `%`: the order will not become smaller than `OrderSize / (1 + SessionReduceOrderMin / 100)`; the default `500` — not less than one sixth of the base. Allowed range `0 .. 5000`; negative values are zeroed (the divisor limit becomes 1, the reduction turns off). The terminal tooltip says "5 times" — by the code the factor is `1 + 500/100 = 6`. |
| **`SessionResetTime`** | `int · 0` | Session decay period in seconds (`0` — off): every `SessionResetTime` seconds, on all coins of the strategy, the accumulated session result is reduced by `10%`, and the non-zero profitable and negative session counters are decreased by `1`. Works only with `IgnoreSession = NO`. |
