# Guide to generating and verifying Moonbot strategies (`FVersion=12`) for AI assistants

For live typed operations through Station MCP / ActiveLib, use the [Station MCP guide](station-mcp-guide.md). This page describes the separate text-import format.

> **Purpose of this document:** A reference of the strategy text import rules, default values and syntax constraints of the Moonbot terminal (`v7.71` / `FVersion=12`) for language models and AI assistants that create, verify and modernize `##Begin_Strategy ... ##End_Strategy` configurations.  
> **Official Moonbot documentation:** [Documentation](https://moonbot.pro/documentation) | [Education](https://moonbot.pro/education)

---

## 1. Structure of the `##Begin_Strategy` import block and default values

When a strategy text block is pasted, the terminal runs a strict sequence:
1. Creates a new strategy with default values.
2. Looks for the `##Begin_Strategy` header and reads the activity flag **from the first line** — `Active=0` (disabled) or `Active=-1` (enabled); the words `YES`/`NO` on this line **are not accepted** and produce the error "Strategy file format error (Active field)", although `YES`/`NO` work on all other lines of the block. **On the second line** it checks the format version `FVersion=12`.
3. Parses `Key=Value` pairs line by line up to the `##End_Strategy` marker, matching the names against strategy parameters **case-sensitively** (for example, the parameter `buyPrice` is written strictly with a lowercase `b`; a wrong name or wrong case is silently ignored and leaves the default!). For integer parameters (`int` / `int64`), the suffixes `K` and `M` multiply the integer by `1000` and `1000000` but **do not allow a decimal point** (`1500K` or `1500000` is correct, while `1.5M` will not parse — the parameter silently keeps its default value).
4. After reading all lines it applies version migrations and forcibly normalizes ranges — the same way as on every save of the strategy (for example, `MShotPriceMin >= 0.001`, `MShotPrice >= MShotPriceMin + 0.001`, `HookTimeFrame` within `0.4..10.0`, `TradesDensity` within `10..100`, `SellSpreadDistance` within `-100..-1`, `TrailingSpread=0 -> 0.1`).

Mandatory skeleton of any generated block:
```ini
##Begin_Strategy
Active=0
FVersion=12
StrategyName=...
SignalType=...
...
##End_Strategy
```

If a parameter line is omitted from the import block, the parameter **does not become `0` or "disabled"** — it keeps its default value:

| Parameter | Default value | Behavior when the line is omitted, and rules for disabling the filter |
| :--- | :---: | :--- |
| **`FVersion`** | `0` (when the line is absent) | Triggers migrations of old versions: at `FVersion=10` the `MShotReplaceDelay` / `HookReplaceDelay` delays are divided by 1000, at `FVersion<12` `TokenTags` is moved to `BinanceTokenTags`, older versions touch trigger keys and `HookAntiPump` (full list — [params/08 §3](params/08-ui-system-and-migrations.md)). Always put `FVersion=12` right after `Active=...`. |
| **`Delta_3h_Max`** | **`20`** (`20%`) | Checks `Max(Delta_3h, Delta_1h) <= 20%` and cuts off volatile coins. **Important:** `Delta_3h_Max=0` **does not disable** the filter — it requires `Delta <= 0%` and blocks the strategy completely! To widen the bounds with `IgnoreDelta=NO`, set `Delta_3h_Max=1000` (and also `Delta2_Max=1000`). |
| **`Delta_BTC_Min` / `Delta_BTC_Max`** | **`-5` / `5`** | Stops entries when the hourly `BTC` move is outside `-5% .. +5%` (likewise `Delta_BTC_24`: `-10..10`, `Delta_Market`: `-5..10`, `Delta_Market_24`: `-10..10`). **Trap:** setting `0 / 0` leaves only `d <= 0` allowed and blocks a rising market! To lift the limits, set wide bounds (`-50` and `50`) or `IgnoreDelta=YES`. |
| **`MarkPriceMin` / `MarkPriceMax`** | **`0` / `1`** | Belongs to the `Filters / Base` subgroup (disabled with `IgnoreBase=YES`, not `IgnorePrice`). With `MarkPriceMin=0` the lower bound is off, while `MarkPriceMax=1` blocks entry when the `MarkPrice` deviation is `> 1%`. For a two-sided corridor set `-X .. +X` (to disable both bounds — `0` and `0`). |
| **`PriceStepMax`** | **`0.5`** (`0.5%`) | Checks `PriceStepMin <= pStep <= PriceStepMax`. **Trap:** `PriceStepMax=0` **does not turn off** the filter — it requires a zero price step and blocks all pairs! To open the filter with `IgnorePrice=NO`, set `PriceStepMax=100`. |
| **`MinVolume` / `MaxVolume`** | **`100` / `100000`** (`100k`) | The constructor default `MaxVolume=100000` cuts off liquid pairs with a daily volume above `100k`, and `MaxVolume=0` means a ceiling of `0$` and blocks 100% of the market. Always set `MaxVolume=100000M` explicitly. |
| **`MinHourlyVolume` / `MaxHourlyVolume`** | **`10` / `10000`** (`10k`) | `MaxHourlyVolume=0` sets a ceiling of `0$` and blocks all pairs. Always set `MaxHourlyVolume=100000M` explicitly. |
| **`MoonIntRiskLevel` / `MoonIntStopLevel`** | **`2` / `4`** | `MoonIntRiskLevel=2` takes into account `@MoonInt` signals on the coin of level `2` and above (`Deep`, `Deadly`, `AdminStop`); `MoonIntStopLevel=4` (default) does not stop the whole strategy on the regular levels `1..3`, but the `AdminStop` signal stops it at any value other than the disabled function. Requires a connected Telegram. |
| **`PenaltyTime`** | **`300`** (5 min) | A 300 s pause on a coin after 3 losing trades in a row (a shared counter across the whole terminal), a manual cancellation or a click on the chart. To disable, set `PenaltyTime=0`. |
| **`NextDetectPenalty`** | **`30`** (30 s) | A pause of `1 + NextDetectPenalty` s before a repeat detect of the same coin by this strategy. |
| **`GlobalDetectPenalty`** | **`0`** (off) | A shared pause on the coin (s) after a detect by any strategy. |
| **`AutoCancelBuy`** | **`300`** (5 min) | Cancels an unfilled `Buy` order (including conditional `BuyStop`/`BuyLimit`) after 300 s. To hold a grid or pending orders, set `AutoCancelBuy=0` (in `MoonShot` it is clamped to `>= 15` s). |
| **`StopLoss` / `AllowedDrop` / `StopLossSpread`** | **`-5` / `-99` / `1`** | `StopLoss` is the level that starts the exit; `AllowedDrop` is the limit down to which the closing `Panic Sell` order is allowed to chase the price (not a loss level). The default `AllowedDrop=-99` (`< -98`) removes the cascade's own price floor: this raises the chance of closing on a fast move at the cost of a larger slippage risk — a risk choice, not a universally safe setting. A too-tight `AllowedDrop` on a squeeze, on the contrary, can leave the order below the market, and the position will not close. There is no fallback floor with `UseStopLoss=NO`: an exit by filters, formula or button obeys the same `AllowedDrop`. Keep `StopLossSpread` close to the real order book depth of the coin (the site recommends `0.4..1.5`): an inflated value on squeezes runs into the exchange price corridor (`-1013` / `-4024` / `51031`). |
| **`TrailingPercent` / `TrailingSpread` / `TakeProfit`** | **`-3` / `0.5` / `1`** | With `UseTrailing=YES` and `UseTakeProfit=YES` the trailing stop fires only on a `3%` pullback from the peak and only while the price is above `+1%` (the `TakeProfit` level) — that is, the peak must rise to about `+4%`; the close goes through `Panic Sell`, the `TakeProfit` level is not guaranteed. Trailing is **enabled by default** (`UseTrailing=YES`, `TrailingPercent=-3`, `TakeProfit=1`): a template without an explicit `UseTrailing=NO` trades with trailing. |

## 2. Mandatory rules of Moonbot math and syntax

0. **The Autotrading module is the condition for links and formulas to work.** Trigger keys (`TriggerKey*`, `TriggerByKey`, `TriggerKeysBL`, `SellByTriggerBL`, `CancelByTriggerBL`), the `CustomEMA` and `SellByCustomEMA` formulas, the `EMA`, `Spread` and `Activity` strategy detectors (and the `SpreadRepeatIfProfit` repeat), strategy sessions (`SessionStrat*`, `SessionIncreaseOrder` / `SessionReduceOrder`) and shot repeats (`MShotRepeat*`) are checked by the terminal **only with the Autotrading module active** (PRO) **or in the terminal's global emulator mode** (Menu → Emulation mode). `EmulatorMode=YES` on an individual strategy does not count as this mode. The coin's market session (`SessionProfitMin` / `SessionProfitMax`) is checked without the module too. Without the module, in live mode, correctly specified link and formula conditions are **skipped**: a slave strategy does not wait for the master and enters on its own, a filter formula does not restrict entry, a key shield blocks nothing (a syntactically wrong formula or key list may still block the strategy earlier). When generating a link or a formula, always tell the user about this condition. Link: `https://moonbot.pro/moonbot-pro/modules/autotrading`. **The Free version** runs only `Delta`, `PumpsDetection`, `MoonShot`, `TopMarket`, `Manual`, `Alerts` (and `Watcher` on Hyperliquid with MoonBonus), with up to 30 active orders; `EMA`, `Telegram`/`MoonNews`, `MoonStrike`, `Liquidations` (futures with a supported liquidation feed, including Binance and Bybit), `MoonHook` (with MoonBonus), `NewListing` (after the agreement) — the PRO version.
1. **No zero ceilings for volume, price step and deltas:**
   * Never set `0` to "disable" the upper bounds `MaxVolume`, `MaxHourlyVolume`, `PriceStepMax`, `Delta_3h_Max`, `Delta2_Max`, `Delta_BTC_Max`, `Delta_Market_Max` — in the filtering code these are live numeric bounds that will block trading. Use wide values (`MaxVolume=100000M`, `MaxHourlyVolume=100000M`, `PriceStepMax=100`, `Delta_3h_Max=1000`, `Delta_BTC_Min=-50`, `Delta_BTC_Max=50`) or disable the corresponding tab with the flag `IgnoreVolume=YES`, `IgnorePrice=YES`, `IgnoreDelta=YES`.
2. **The `PriceAdjust` scale in `Short` strategies:**
   * In Moonbot, price levels for `Short` are computed by the formula `P_level = P_entry / (1 + d / 100)`. Therefore `StopLoss=-50` in a short puts the stop level at the price `2 * P_entry` (a `+100%` rise of the asset price against the short, which on a linear futures contract gives `-100%` PnL of the position notional before leverage), and `StopLoss=-80` — at the price `5 * P_entry` (a `+400%` rise of the asset price and `-400%` of the order notional). So in a short keep the main stop enabled with a moderate `StopLoss`, set `StopAboveLiq > 0` and, where the exchange supports it, `UseMarketOrder = YES`. **Do not tighten** `AllowedDrop` in a short: it is not a loss level but the chase limit of the closing order — a tight `AllowedDrop` on a squeeze will leave it below the market, and the position will not close ([chapter 06](../concepts/06-orders-exits-and-stops-cascade.md)).
   * Likewise, in `PriceDownAllowedDrop` on `Short`, values `<= -100` drive the denominator `1 + d/100` to `<= 0` and block `PriceDown` lowering. Set `PriceDownAllowedDrop=0` (down to the entry price) or `-5..-15`.
3. **Syntax and indexing of the `CustomEMA` and `SellByCustomEMA` formulas:**
   * **Grouping parentheses are forbidden:** the `CustomEMA` parser supports the logical operators `AND` and `OR` (`AND` has higher priority) but **does not support grouping parentheses around logical expressions** such as `(EMA(...) AND ...)` — parentheses are allowed only around the arguments of the function itself, `Func(X, Y)`.
   * **`EMA(X, Y)`, `Avg(X, Y)`, `BTC(X, Y)` and `MAvg(X, Y)`:** both arguments are points in time (`1s..300s`, `2m..90m`, `1h..48h`; without a suffix the number is treated as seconds `s`, and `0` is not allowed in price functions — for the current price use `1s`). The function computes the price change from `X` to `Y` by the formula `(V_Y / V_X - 1) * 100%`: the first argument `X` is always further in the past, and the second `Y` is closer to the present (for example, `EMA(5m, 1s) < -2.5` or `Avg(4s, 1s) > 0.15`). Second-based `EMA` values are smoothed; minute and hour `EMA` (and `BTC`, `MAvg`) are the average price of the minute or hour that was `N` ago (hourly — without the last hour); `Avg(X, Y)` is a history point of the reference price `X` ago without smoothing. **The `Avg` history depth is limited** (on a VDS and on the kernel — a few minutes, on a regular PC — up to an hour depending on memory): until the buffer has accumulated data the filter does not pass, and when the window is longer than the filled buffer the comparison is made against the oldest stored point rather than the needed moment. For windows longer than a few minutes use `EMA` with minute or hour arguments (for example, `EMA(30m, 1s) < -2`); `Avg` — for second-scale reversals. Availability of long hourly windows depends on the accumulated candle history: with a normal load it covers about `41h`, and windows `42h..48h`, although the parser accepts them, usually remain `no data`.
   * **`MAX(X, Y)` and `MIN(X, Y)`:** the first argument `X` sets the extreme window in minutes **`5m..90m`** in steps of `5m` (smaller values and the `s` suffix are converted to minutes rounded to `5m`, so `10s` turns into `10m`) or in hours **`1h..48h`** (but data is usually available only up to `~41h` — see above); the second argument `Y` (`1s..300s`, `2m..90m`, `1h..48h`) is computed as `EMA(Y)`. **The window does not include the last segment:** minute `MAX(Nm)` is the extreme over `N` minutes that ended about a minute ago; hourly `MAX(Nh)` is over `N` hours that ended **an hour ago** (`MAX(1h)` is the maximum from the 60th to the 120th minute ago). This way the current price may be above the maximum, and the formula defines a new high. If you need the level of the last hour specifically, write `MAX(60m, 1s)`, not `MAX(1h, 1s)`. When the current price is below the maximum, `MAX(X, Y)` is negative (`<= 0`), so to buy after a 5% pullback from the maximum you must write the minus sign: **`MAX(15m, 1s) < -5`** (the condition `< 5` without the minus will pass all coins that are not 5% above their maximum — that is, practically the whole market).
   * **`Vol(X, Y)`:** compares the per-minute volume rate over window `Y` with window `X` (allowed argument values: `0`, `5s`, `15s`, `30s`, `1m`, `3m`, `5m`, `15m`, `30m`, `1h`, `3h`, `24h`). With `X = 0` (or `0s`) the denominator equals `1`, and the function returns the volume rate of window `Y` normalized to 1 minute (`$/min`) (for example, `Vol(0s, 15s) > 120000` or `Vol(0, 1m) > 50000`). **Attention:** to the right of the comparison sign in `CustomEMA` the **`k`/`m` suffixes are not supported** — write the full number `100000` (writing `100k` causes a parser error!).
   * **`Arb(Exch)`:** computes the cross-exchange spread by the formula **`(ExternalPrice / LocalPrice - 1) * 100%`**. `Arb(BinanceF) < -2.5` means that on the external exchange (`BinanceF`) the price is `2.5%` **lower (cheaper)** than on the terminal's local exchange (`> 2.5` — the external exchange is `2.5%` more expensive than the local one). Supported venue codes: `BinanceS`, `BinanceF`, `BinanceQ`, `BybitS`, `BybitF`, `OKXS`, `OKXF`, `BitgetS`, `BitgetF`, `GateS`, `GateF`, `HtxS`, `HL_S`, `HL_F`, `HL_<dex>`, `UpBit`, `BinAlpha` and `*`. **Do not use the `Forex` code in formulas:** the parser searches for the `OR` operator as a case-insensitive substring and cuts `F|orex`, the whole formula is marked erroneous and blocks entries (Forex quotes are visible only on the chart in the arbitrage module).
   * **Collector thresholds (the comparison is skipped, the value is written to the report; data is still required — without trades over the `Vol` window or without history the condition is false):**
     * for all price functions (`EMA`, `Avg`, `BTC`, `MAvg`, `MAX`, `MIN`, `Arb`): with the `>` sign always true at a threshold **`<= -887`** (standard form `> -888`), with the `<` sign — at a threshold **`>= 887`** (`< 888`);
     * for `Vol(X, Y)`: the only collector threshold is with the `>` sign at a threshold **`<= 0`** (**`Vol(X, Y) > 0`**); the threshold `< 888` for `Vol` is checked as a regular volume filter `< 888$`!
   * **The `SellByCustomEMA` field:** to disable it, leave the field empty (`SellByCustomEMA=`). `SellByCustomEMA=0` causes a syntax error and blocks the strategy, and the collector threshold `> -888` inside `SellByCustomEMA` with the default `SellEMACheckEnter=YES` forbids buying wherever the formula has data (the exit condition is already true at entry), and with `NO` closes the position right after the purchase.
4. **How `IgnoreFilters` and `IgnoreBase` affect `CustomEMA` and `SignalType=EMA`:**
   * For all strategies except `EMA`, the `CustomEMA` check runs inside the `Filters / Base` group and is skipped with `IgnoreFilters=YES` or `IgnoreBase=YES`.
   * In a strategy with **`SignalType=EMA`**, enabling `IgnoreFilters=YES` disables the general filter groups (`Base..Delta`), but its detector checks the `CustomEMA` formula itself and keeps checking it; however, the `NextDetectPenalty` and `StrategyPenalty` pauses stop acting, and the strategy enters on every pass.
   * The flag `IgnoreFilters=YES` also **does not disable**: `SessionPenaltyTime` (needs `IgnoreSession=YES`), `Triggers`, `SellByCustomEMA`, `CoinsWhiteList`/`CoinsBlackList`/`DynWL`/`DynBL`, `OnlyNewListing`, `DontTradeListing`, `LeveragedTokens`, `ListedType` and the `Quantitative Rules` protection.
5. **Exact mechanics of `MoonShot` and `MoonHook`:**
   * In `MoonShot` all `MShotAdd*` terms are non-negative and only deepen the order (only `MShotAddMarkDelta` depends on the order side; the sum is capped by `MaxModifier`), and **`MShotMinusSatoshi=YES`** merely keeps the limit order from sitting right against the reference price `MShotUsePrice` — important for coins with a coarse price step.
   * `BuyOrderReduce > 0` in `MoonHook` and `Spread` works the same way: the estimated volume from the trade-feed turnover becomes an **entry filter** (a signal with an estimate below `MinReducedSize` is rejected) and a **cap on the order size** (the order is cut down to the estimate, not below the exchange minimum). The reduction is not applied to a manual hook.
6. **Safe trigger setup (`Master → Slave`):**
   * In the code, the `SellByTriggerBL` check is nested inside the `TriggerKeysBL` check: if a key is listed in `SellByTriggerBL` but **not in `TriggerKeysBL`**, the emergency sell by `SellByTriggerBL` **will not fire at all**! Always duplicate the keys from `SellByTriggerBL` in `TriggerKeysBL` with a non-zero blocking time.
   * Clearing keys via `ClearTriggerKeys`, `ClearTriggersBelow` and `ClearTriggersAbove` is invoked only when the strategy itself has a non-zero key for the corresponding event (`TriggerKey > 0` on detect, `TriggerKeyBuy > 0` on buy, etc.). Moreover, in `TriggerAllMarkets=YES` mode an attempt to clear its own `TriggerKey` via `ClearTriggerKeys` will not work, because the global activation loop immediately writes this key to all markets again. A key without a time does not act: `TriggerSecondsBL` is `0` by default, so give blocking keys a time right in the list (`TriggerKeysBL=102=120`), and in `SellByTriggerBL` write only the numbers.
   * On a master `MoonShot`, do not enable `ActiveTrigger=YES` together with `TriggerKeyBuy` (otherwise the buy key will stay active the whole time the limit order sits in the order book — before the purchase). For a scout in the emulator (`EmulatorMode=YES`) on spot, set `AutoSell=NO` so that virtual trades do not change its session and pauses and do not keep the coin busy; on futures `AutoSell` is forced to `YES` — there the scout needs conditions to close the virtual position (`SellPrice`, `StopLoss`), otherwise it will not re-arm while it is open; `MShotRepeatAfterBuy=YES` on `MoonShot` is a repeat entry with an open position within the `MShotRepeatWait` window, not an exit.

## 3. Verified configuration-node templates (`FVersion=12`)

* **Excluding leveraged tokens, stablecoins and pairs under monitoring:**
  ```ini
  CoinsBlackList=*3L,*3S,*5L,*5S,*DOWN,USDC,FDUSD,USDE,TUSD,DAI,EUR
  BinanceTokenTags=!Monitoring !Alpha
  ```
  Do not add the `*UP` mask for `...UP` tokens blindly: it will also cut off regular coins ending in `UP` (for example, `JUP`) — list such tokens by ticker.
* **Switching to the second stop loss (`SecondStopLoss`):** the second stop is enabled when, after `TimeToSwitch2Stop` seconds from the placement of the `Sell` order, the trade has its stop loss enabled and the price is on the favorable side of the `PriceToSwitch2Stop` threshold (for a long — `Bid` above the "entry + threshold" level, for a short — below the mirrored level; the template below is for a long). If the trade sits deeper, the terminal waits for the price to return past the threshold and then switches the stop. For the timer switch to work in a loss too, set a low `PriceToSwitch2Stop` threshold — the switch will fail only deeper than it. The second stop has no chase limit of its own: after it fires, the main `AllowedDrop` applies (`AllowedDrop3` concerns only the third stop), so set the limit in `AllowedDrop`:
  ```ini
  UseStopLoss=YES
  UseSecondStop=YES
  TimeToSwitch2Stop=15
  PriceToSwitch2Stop=-10.0
  SecondStopLoss=-0.5
  AllowedDrop=-10.0
  ```
* **Exponential order grids (`MultiOrders`):**
  * with `OrderSizeKind=Exponential`, the volume of the $k$-th order is computed as `OrderSize * (|OrderSizeStep| / 100)^(k - 1)`: `OrderSizeStep=100` gives equal orders (`1.0x`), `130` multiplies each next order by `1.3x`, `200` doubles it (`2.0x`), and `0` zeroes the volume of all orders from the 2nd on;
  * with `BuyStepKind=Exponential`, the price of the $k$-th order is computed by the power formula `Price1 * (1 + BuyPriceStep * (k - 1) / 100)^k` for Long (and by dividing by this multiplier for Short).
